# Boxty Demo

A full-stack modular monolith starter framework, with multi-tenancy, multi role, fine grained CRUD permissioning autogenerated for every entity. 

Blazor Webassembly frontend, .NET Core WebAPI backend. Postgres DB. Uses Keycloak for authentication and authorisation at the role level (.NET backend deals with permissions).

## Getting Started

### Starting the Application

Start all services using Docker Compose:

```bash
docker compose up --build
```

This will:
- Build and start the client application (Blazor WebAssembly)
- Build and start the server application (ASP.NET Core API)
- Start all dependent services (database, etc.)
- Enable hot reload for automatic updates during development

**Note:** Make sure Docker Desktop (or Docker Engine) is running before executing the docker compose command.

Once the application is running, access it at **http://localhost:5004**

**Default Login Credentials:**
- **Username:** `admin`
- **Password:** `123`

### Restarting Individual Services

To rebuild and restart a specific service:

```bash
# Restart the client only
docker compose up --build chapp.client

# Restart the server only
docker compose up --build chapp.server
```

## Stopping the Applications

Press `Ctrl+C` in the terminal, or run:

```bash
docker compose down
```

## Configuration

### SMTP Email Configuration

SMTP defaults are seeded into the Settings database by
[SettingsSeedData](Boxty/ServerApp/Modules/Settings/Infrastructure/Database/SettingsSeedData.cs)
during module startup, immediately after migrations, following the same pattern
as the root admin seed in UserManagement. No separate SQL restore or manual
post-migration command is required.

The seed copies the former appsettings values: `info@boxty.com`, sender name
`Boxty System`, host `smtp.ionos.co.uk`, port `465`, username `emailsmtp@boxty.com`,
and `EnableEmailSending = true`. The password remains the placeholder
`YOUR-SMTP-PASSWORD`; supply a real credential securely before enabling delivery.
Seeding only runs when the SMTP table is empty, including archived records.
Existing or edited settings are never overwritten.

**Common SMTP Providers:**
- **Gmail**: `smtp.gmail.com`, port `587` (TLS) or `465` (SSL)
- **Outlook/Office365**: `smtp.office365.com`, port `587`
- **SendGrid**: `smtp.sendgrid.net`, port `587`
- **AWS SES**: region-specific endpoint, port `587`

**Note:** Set `EnableEmailSending` to `false` during development if you want to disable email functionality.

**Settings > Email Sending** uses the shared `CrudForm` directly, without custom
loading or save/delete callbacks. `SmtpSettings` accepts a supplied `Model` and
`FormMode`; without them it renders a blank new configuration.

The base form currently does not load singleton settings,
transition automatically from create to edit after saving, or reload/reset after
deletion. Those capabilities must be added to the base components/services before
this tab can automatically edit the saved singleton.
Repeated saves of a newly created model are not guaranteed to update the same
record until the base form handles the create-to-edit transition.

The config-defaults endpoint has been removed. **Runtime integration gap:**
the base email service and user creation/password-reset commands still depend on
`AppOptions.Email`, not the Settings database. With the `Email` appsettings section
removed, those paths require base service integration with the saved SMTP record
before email-related operations can work. This change does not modify base services.

## Development Scripts

### Create a New Module

Use the installed Boxty module template to create a new module in the same structure as `DBExplorer`.

**Install template:**

```bash
dotnet new install ./templates
```

Run this from the demo repository root. After updating the templates, refresh the installed copies:

```bash
dotnet new install ./templates --force
```

**Create a new module:**

```bash
dotnet new boxty-module --moduleName "DemoModule" --entityName "Invoice"
```

> Run from the demo repository root (or use `--output <demo-root>`). Do not output directly into the `Modules` folder itself.

This creates a module under:

```text
Boxty/ServerApp/Modules/DemoModule/
Boxty/SharedApp/DTOs/DemoModule/
```

The generated structure mirrors the `DBExplorer` conventions:

```text
Boxty/ServerApp/Modules/DemoModule/
├── Entities/
├── Infrastructure/
│   ├── Database/
│   │   ├── Configurations/InvoiceConfiguration.cs
│   │   ├── DesignTimeDbContextFactory.cs
│   │   └── DemoModuleDbContext.cs
│   ├── Mappers/
│   └── DemoModuleModule.cs
├── Application/
├── Endpoints/
├── Services/
└── *.csproj files

Boxty/SharedApp/DTOs/DemoModule/
└── InvoiceDto.cs
```

The generated projects include their framework packages and project references. The DbContext uses the entity name (`Invoice`), not the module name, and includes a design-time factory so migration generation does not start the full application.

**Wire the new module into the host (required once per module):**

The template adds new files only; it does not overwrite the existing WebApi project or startup code.

```bash
dotnet add Boxty/ServerApp/WebApi/WebApi.csproj reference \
  Boxty/ServerApp/Modules/DemoModule/Infrastructure/Boxty.ServerApp.Modules.DemoModule.Infrastructure.csproj \
  Boxty/ServerApp/Modules/DemoModule/Endpoints/Boxty.ServerApp.Modules.DemoModule.Endpoints.csproj

dotnet sln Boxty/ServerApp/ServerApp.sln add \
  Boxty/ServerApp/Modules/DemoModule/*/*.csproj
```

In [Boxty/ServerApp/WebApi/Program.cs](Boxty/ServerApp/WebApi/Program.cs), add `using Boxty.ServerApp.Modules.DemoModule.Infrastructure;` and add `typeof(DemoModuleModule),` to the existing `moduleTypes` list, keeping the other modules.

Then restore and verify the host:

```bash
dotnet build Boxty/ServerApp/WebApi/WebApi.csproj
```

Both Infrastructure and Endpoints references are needed: Infrastructure supplies the DbContext and mappers, while Endpoints must be available for runtime endpoint discovery.

### Create a New Entity, DTO, and Mapper

Use the entity template only after a module already exists. This does not create a new module; it adds a new entity inside an existing module folder.

**Install template:**

```bash
dotnet new install ./templates
```

**Generate a new entity in an existing module:**

```bash
dotnet new boxty-entity --moduleName "DemoModule" --entityName "Payment"
```

> Run from the demo repository root (or use `--output <demo-root>`), not from inside the module. Use a new entity name; do not use `--force` to overwrite an entity you have already customized.

This creates files like:

```text
Boxty/ServerApp/Modules/DemoModule/Entities/Payment.cs
Boxty/ServerApp/Modules/DemoModule/Endpoints/PaymentEndpoints.cs
Boxty/ServerApp/Modules/DemoModule/Infrastructure/Mappers/PaymentMapper.cs
Boxty/ServerApp/Modules/DemoModule/Infrastructure/Database/Configurations/PaymentConfiguration.cs
Boxty/SharedApp/DTOs/DemoModule/PaymentDto.cs
```

The generated classes follow the repo conventions:
- entity inherits `BaseEntity<Payment>` and `IEntity`
- DTO inherits `BaseDto<PaymentDto>`, `IDto`, `IAuditDto`, and `IAutoCrud`
- mapper implements all four `IMapper<Payment, PaymentDto>` methods using explicit mapping, compatible with the field generator
- namespaces use the target module name, for example `Boxty.ServerApp.Modules.DemoModule.Entities`
- EF configuration registers the entity, table/schema, and UUID default through the DbContext's existing `ApplyConfigurationsFromAssembly` call

No additional DbSet or project reference is required for each entity. For older modules, ensure the DbContext calls `modelBuilder.ApplyConfigurationsFromAssembly(typeof(DemoModuleDbContext).Assembly)` and has a design-time factory, and complete the host wiring above once. Generated table names append `s` to the entity name; adjust `ToTable` in the configuration if you need a different plural.

After changing properties manually, update both the DTO and mapper too, or use the field generator below.

### Add Fields to an Existing Entity/DTO/Mapper

Use the field generator for incremental property additions after the entity already exists.

```bash
cd <repo-root>/boxty.demo/scripts
./generate-fields.sh
```

It will prompt for:
1. the module
2. the entity name
3. one or more fields, for example:

```text
public required string Name, public string Description, public Guid TenantId
```

and then update the matching entity, DTO, and mapper in place.

### Running Database Migrations

After generating entities or making changes to your entity models, you need to create and apply database migrations to update the database schema.

**Usage:**

```bash
cd Boxty/ServerApp
./run-migrations.sh
```

The script will:
1. Display available modules with database contexts
2. Prompt you to select which module's database to migrate
3. Ask for a migration name (e.g., `AddProductEntity`, `UpdateUserFields`)
4. Generate the migration files in the module's `Database/Migrations` folder
5. Stop with a nonzero exit code if restore, build, or migration generation fails

The script restores the selected Infrastructure project and WebApi before running EF, and loads configuration from the WebApi directory. It uses `ASPNETCORE_ENVIRONMENT` if set, otherwise `Development`. Configure `ConnectionStrings:DefaultConnection` for that environment, or supply `ConnectionStrings__DefaultConnection` through an environment variable. No local configuration file or guessed credentials are generated.

To explicitly select a different environment:

```bash
ASPNETCORE_ENVIRONMENT=Staging ./run-migrations.sh
```

**Prerequisites:**
- Install the EF CLI if it is missing (`dotnet tool install --global dotnet-ef --version '9.*'`)
- Complete the new module's host wiring described above
- Provide the environment's `DefaultConnection` configuration
- Make sure your entity changes are saved before running migrations
- The database is not required just to generate migrations; it must be available when applying them

**Example Workflow:**
```bash
# 1. Generate a new entity from the demo repository root
dotnet new boxty-entity --moduleName "DemoModule" --entityName "Payment"

# 2. Create the database migration
cd Boxty/ServerApp
./run-migrations.sh
# Select module number corresponding to where you added the entity
# Enter migration name: AddPaymentEntity

# 3. Review the generated migration, then apply it explicitly
cd WebApi
ASPNETCORE_ENVIRONMENT=Development dotnet ef database update \
  --context DemoModuleDbContext \
  --project ../Modules/DemoModule/Infrastructure/Boxty.ServerApp.Modules.DemoModule.Infrastructure.csproj \
  --startup-project WebApi.csproj
```

**Note:** The migration script only generates migrations. The generated module also applies pending migrations at application startup, so review them before restarting the application.

### Template Regression Check

```bash
python3 scripts/test-templates.py
```

This uses an isolated template installation and temporary project to build generated modules, verify mappers and DbContext registrations, and generate migrations before and after adding entities. It requires Python 3, the .NET SDK, and `dotnet-ef`, but no running database. It does not change your application or installed templates.
